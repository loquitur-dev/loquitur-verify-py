# Code of conduct

**Status:** baseline code of conduct  
**Applies to:** Loquitur repositories, issues, pull requests, discussions, documentation spaces, and
project communication channels

Loquitur is a protocol for verifiable evidence behind real-world asset claims, and its code is
security-sensitive. The quality of the project depends on rigorous technical disagreement, precise
review, and professional conduct. This code of conduct is the baseline for that work.

## 1. Expected behavior

Participants are expected to:

- act professionally and respectfully;
- assume good faith while still requiring evidence;
- criticize ideas, code, claims, and designs rather than attacking people;
- keep reviews specific, actionable, and grounded in facts;
- disclose uncertainty instead of overstating confidence;
- avoid unsupported claims about security, compliance, production readiness, or external
  commitments;
- respect confidentiality around issuer evidence, non-public discussions, and private artifacts;
- report security issues through `SECURITY.md`, not public issue threads.

Strong technical disagreement is allowed and expected. Harassment, humiliation, threats, or personal
attacks are not.

## 2. Unacceptable behavior

Unacceptable behavior includes:

- harassment, intimidation, stalking, or threats;
- discriminatory or degrading comments;
- sexualized language or imagery in project spaces;
- publishing private information without permission;
- sharing confidential issuer, reviewer, security, or business information;
- intentionally misrepresenting project capabilities;
- pressuring contributors to make unsupported claims;
- bypassing coordinated disclosure for security issues;
- repeated disruption of technical discussion after the maintainer intervenes.

## 3. Security and confidentiality expectations

Because Loquitur deals with evidence integrity and private bundle disclosure boundaries,
participants must not post:

- private keys;
- credentials;
- real issuer evidence;
- confidential reviewer information;
- non-public business documents;
- production secrets;
- exploit details before coordinated disclosure.

If sensitive material is accidentally posted, notify the maintainer immediately and avoid spreading
it further.

## 4. Enforcement model

Enforcement is handled by the project maintainer, one person, as section 6 states. Depending on
severity, the maintainer may:

- ask for clarification or edits;
- remove or hide comments;
- close issues or pull requests;
- pause a discussion;
- restrict participation temporarily or permanently;
- escalate security-sensitive incidents through the `SECURITY.md` process.

Enforcement decisions should be proportionate, documented when appropriate, and focused on
protecting the project and its contributors.

## 5. Reporting conduct issues

**Use GitHub's private vulnerability reporting on this repository**: open the *Security*
tab and choose *Report a vulnerability*, and state that the report is a conduct matter
rather than a vulnerability. It is visible only to the maintainer and needs nothing set up on
your side. It is the first of the two private channels `SECURITY.md` documents.

If private reporting is unavailable to you, write to **security@loquitur.dev**, the second
channel `SECURITY.md` documents, and say that the message is a conduct report. Keep the
details out of the first message if you prefer: the maintainer replies and agrees a private
channel for them. Do not describe a conduct report in a public issue.

There is no separate conduct mailbox: a conduct report reaches the maintainer through the same
two channels as a security report.

If a conduct report also involves a vulnerability, exploit, secret, or private evidence, use the
security process in `SECURITY.md` or ask the maintainer for a secure reporting channel.

## 6. Maturity

Current state:

- no independent conduct committee exists;
- no foundation or other governance body exists;
- no public appeals process is formalized;
- the maintainer is responsible for enforcement. There is one; a reader should know that a
  report goes to the same person who wrote the code.
